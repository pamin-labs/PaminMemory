# Cloudflare Workers

How a Cloudflare Worker in TypeScript meets `core.md`; read it first. The directory's `AGENTS.md` says what its Workers route and names their modules.

- **No business logic.** A Worker routes calls, forwards what the platform or a gateway has already decided (a signed identity, place headers from Cloudflare's own lookup), and starts, wakes and fails over containers; anything about users, tenants, keys, limits, entitlements or content belongs to the server, the gateway or a module.
- **Pure functions apart from the runtime.** Path rules, header handling, failover, picking an instance, catalogue parsing and checks of settings live in their own modules, each tested with Vitest without the Workers runtime; the entry file only wires them to the Worker and its Durable Objects.
- **No decisions in the entry file.** Every decision (which port, which headers pass, whether a body can be buffered, when to retry a start, how long to wait for health) is a tested function in one of those modules, and settings read from `env` are parsed by a tested function there. Timeouts and limits are named constants in those modules, never written inline. The one check the entry file keeps is the runtime's own state, such as whether a container is already running.
- **No non-null assertions.** A container is read through the Durable Object's guarded getter, which throws a clear error when the class has none.
- **Every module is named by its path** in the directory's `AGENTS.md`, with what it is for. A test fails on a TypeScript file in a folder that file does not name (tests aside) and on a named file that is gone, so a new module is described there first.
- **A request without `Content-Length`** is handled explicitly: streamed, or read up to a limit; it is never refused by default.
- **Ports and path prefixes are written once,** in one module, and a test or the catalogue generator checks them against the services, their `.env.example` and any client that names them.
- **No user-facing text.** A Worker answers with status codes, headers and the declared problem bodies only; anything a user reads comes from the app's messages or the server, in the user's locale.
- **Security headers** are set by one function on every answer a Worker makes; assets the platform serves without running the Worker get the same headers from its headers file, and a test checks the two agree.
- **Config.** The Wrangler config is the source of names, domains, accounts and environments, never code or scripts. Environments do not inherit containers, Durable Objects, bindings, routes or secrets, so each lists its own, and a test checks the names agree. Generated binding types are regenerated with `wrangler types` after a config change, never edited.
- **One deploy path.** Deploys and local settings go only through the repository's `ops` command, which reads the environment's settings from the deployment's secret manager once, checks them, and sends secrets through stdin so they are written nowhere. Nobody runs a Wrangler command that changes a Worker by hand (`deploy`, `versions upload`, a `secret` write, `triggers deploy`, `delete`); a repository hook refuses those to agents, while read-only commands and `--dry-run` pass. A rollback is the engineer's, by hand, and the next `ops` deploy brings the Worker back in step.
- **Typed end to end.** No `any`, and no `as` cast except on generated types. Values from settings, another service or a request are checked with a guard that has a test with malformed input, and a `switch` over a closed set ends with `default: x satisfies never`.
- **Dependencies** are pinned exactly, and a check fails on any that is unused. Biome warnings fail the check, and after upgrading Biome its `biome migrate` runs.
