# Prospective external model identity

These guards apply to future setup/trials only. The archived trials did not use them; they establish no historical model identity or performance result. `run.py.in` and `build.py.in` remain untouched.

Prepare ready model assets and a reviewed **private mode0600 JSON model plan** in a separate invocation before guarded setup or trials. Trace each compared executable's actual embedding/reranker model selection, revision, tokenizer inputs, prepared-copy key, attention selection, external tensor locations and native source record. The plan must include the union of assets needed by all compared arms, with separate model entries where their selected graphs differ. Do not generate the expected plan from a trial's mutable current state. Read ONNX external-data references during preparation and list every referenced weight in `graph_external_weights`; this guard compares the reviewed relationship and graph bytes, rather than reinterpreting a changed graph to choose new expected weights.

The plan has `version:1`, a nonempty `selection_provenance` explaining those executable/commit/revision decisions, and a nonempty `models` list. Each model has:

- `name`, `load_graph` (the actual selected prepared graph), and `asset_directories` (only its selected hub revision and prepared-copy directories, relative to the pinned cache).
- `assets`, with nonempty lists for all five roles: `source`, `tokenizer`, `prepared_graph`, `external_weights`, and `metadata`. Paths are relative to the cache. Include tokenizer configuration/vocabulary/model configuration, every prepared graph candidate, attention decision markers, and native `.source` selection/provenance records. Explicitly include both a hub source link and its owned blob if release can remove both.
- `graph_external_weights`, mapping **every** `prepared_graph` path to its nonempty list of bound `external_weights`. Include the selected attention graph and original prepared graph when both exist. All declared weights must be referenced.

For example, a tiny inert model's role map can use `revision/source.onnx`, `revision/tokenizer.json`, `revision/config.json`, `prepared/key/model.onnx`, `prepared/key/model.onnx.data`, `prepared/key/attention.unfused`, and `prepared/native.source`. The graph role contains `prepared/key/model.onnx`, its weight relationship contains `prepared/key/model.onnx.data`, and configuration/decision/source records belong to metadata. The directory list is `revision` and `prepared/key`. Actual plans must use the selected executable's real complete files and paths; these names are illustrative.

Create the new external manifest beside the copied wrapper helpers:

```sh
python3 model-guards.py.in RESOLVED_MODEL_CACHE PRIVATE_PLAN NEW_PRIVATE_MODEL_MANIFEST
```

The manifest must be outside the cache, setup home, seed and trial output. The preparer refuses an existing output and writes mode0600. It fingerprints each declared file's SHA-256, bytes, mode, resolved target and parent/leaf symlink targets. Links may resolve only inside the pinned real cache directory. Selected revision/prepared directories are inventoried completely, rejecting undeclared files (including new attention graphs or markers). Unrelated cached revisions and unused prepared copies are not scanned. The native empty `used` stamp may be created/touched in a selected prepared directory; nonempty or linked stamps fail. Modification times are not identity fields because native loading touches the usage stamp.

Normally all source files must stay present. The native exporter may remove an owned original source on first load. Only when the model plan explicitly sets `allow_source_release:true`, supplies nonempty `source_release_provenance`, maps **each** source path in `source_records` to a bound metadata file, and declares `source_origins` plus `source_blob_targets`, is absence permitted. `source_origins` maps each source asset to its original declared leaf path (a plain file maps to itself). `source_blob_targets` maps each linked original leaf to its explicitly declared owned blob; use an empty map for plain files. The leaf and blob must both be source assets, share the same original leaf and provenance record, and any surviving leaf link must resolve to exactly that owned blob. That record must have the native four-line format (source name, byte length, modification timestamp, `sha256 DIGEST`). The recorded source name must equal the declared original leaf basename, not the content-addressed blob basename; every present leaf/blob must match the record's digest/length. Already released originals can be prepared only with that same retained digest provenance. The original source leaf/blob can disappear, but cannot be redirected, replaced, or changed. Both deletion orders are accepted: a removed leaf may leave its unchanged blob, or a removed blob may briefly leave the original unchanged dangling leaf link. That dangling link remains inventoried and its exact target is checked against the prepared expectation. For a hub leaf such as `revision/onnx/model_int8.onnx` pointing at `blobs/<64-hex-name>`, map both paths in `source_origins` to that original leaf and map the leaf to the blob in `source_blob_targets`; its native record names `model_int8.onnx`. Metadata records, tokenizers, prepared graphs and external weights remain mandatory and byte-identical. Independently settle preparation/fusion and retain the native source record before preparing this manifest; guarded setup does not approve creating a new executable graph or rewriting provenance.

Add `--model-manifest NEW_PRIVATE_MODEL_MANIFEST` before the `setup` or `trials` subcommand. Setup requires its home's `models` link to point at the manifest's cache. Trials require the fixture manifest's model target to match. The wrapper checks the immutable supplied manifest bytes/permissions and selected assets before each setup launch, immediately before each of the nine trial launches (after copy preparation), after each completed arm outside its clock, and after the full trial sequence. Failures retain a model endpoint result or failure class in the private record, with existing native/fixture hooks and process-state restoration preserved.

Keep the full plan/manifest and configuration records private: paths and source/file hashes can reveal sensitive information. Publish only sanitized aggregate selected-model/asset/released-source counts, excluding manifest digests and path/role mappings. The record omits the expected model contents. The trusted preparation plan establishes which files are needed; these checks cannot establish an omitted model's identity, prove actual process mappings, or detect a mutation restored between endpoints.

`test-model-guards.py.in`, `test-fixture-guards.py.in`, and `test-native-build-guards.py.in` use tiny fake files and mock processes only. They cover graph/weight/tokenizer/source/metadata changes, selection/inventory changes, symlink safety, explicit source-release provenance, manifest privacy/immutability, setup and per-arm failure, exact nine endpoint counts, hook/environment/argv restoration, and optimized-Python rejection. No real model, PostgreSQL, native load, Cargo build, or performance measurement is run.

Prospective trials also bind retained actual provider assignments to the selected plan by role. Both provider output and plan must contain exactly `embedding` and `reranker`. Each absolute `model_graph` resolves to that role's declared `load_graph`, and its assignment must contain positive CPU nodes only. Another bound inventory graph, swapped roles, empty/missing provider evidence, and non-CPU assignments fail before an arm endpoint is recorded or the run completes. The frozen historical parser and historical evidence remain unchanged.

Restart setup and trials require `build_kind:restart-trial`, the restart scratch target, matching before/after source hashes and an actual fresh `scratch_restart_floor` compiler artifact from that checkout. Conversion-only build attestations cannot launch either mode. Setup captures output outside timing and requires one `RESTART_JSON` open row; bootstrap also requires the empty-collection path, and seed requires its completion row. An exit-zero executable reporting zero tests fails instead of marking setup finished.
