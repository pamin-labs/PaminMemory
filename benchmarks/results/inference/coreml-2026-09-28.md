# CoreML normalization investigation (2026-09-28)

These are numerical diagnostics and single-pair forward timings, not accepted
retrieval improvements. No nDCG/recall or energy gain is claimed.

## Conditions

- Apple M4, Mac16,12, 10 logical CPU cores, 32 GiB RAM.
- macOS 26.6.2, build 25G83; Rust `ort` 2.0.0-rc.13.
  Runtime build: `rel-1.28.0`, commit `da9b5e3`, Release.
- `onnx-community/bge-reranker-v2-m3-ONNX`, immutable revision
  `6f5ff65298512715a1e669753bc754d2bc8f367b`, `onnx/model_fp16.onnx`.
- The same weights and input IDs in all arms. CPU uses this fp16 export too,
  **not** the product's normal CPU int8 export.
- Graph optimization level 3, 10 intra-op threads, spinning disabled. ORT
  profiling enabled; CoreML compute-plan profiling enabled where applicable.
- Query: `How does memory retrieval work?`
- Document: `A memory system stores evidence so that later questions can
  retrieve accurate facts. ` repeated twice, including the trailing space.
- Batch 1, 48 tokens, no padding in the timing pair. Warm median is passes
  3 through 8 of nine forwards. Separate runs on a shared machine, not rotated
  paired latency trials. Tokenization and complete retrieval are excluded.

| Original / static MLProgram, CPU+GPU | GPU path | about 22.65 ms | -1.15583026 | 0.00110805 |
| Original / static MLProgram, ALL | Mostly ANE | about 10.54 ms | -5.08593750 | **3.92899919** |

ALL permits CPU, GPU and ANE; it does not prove ANE participation. The fp32
normalization variant's compute plan assigned 49 normalizations and all its
other reported operations to GPU. It must not be described as an ANE repair.

The CPU logits also change slightly with the graph rewrites: -1.15626812
for native fp16 normalization and -1.15785253 for the combined native
normalization/GELU graph. Differences from the original CPU reference must
not all be attributed to hardware.

The original dynamic default NeuralNetwork arm supported only 52 of 1,420
nodes. Its nine-forward ORT trace attributed 2,175 ms to CPU kernels and
23 ms to CoreML kernels. Dynamic MLProgram covered 1,312 nodes but split into
51 partitions and was slower in the diagnostic. Static shapes reduced this
to two partitions; correct arithmetic remains a separate requirement.

## Numerical evidence

The CPU trace of the native-normalization graph found large intermediate
values. For normalization 38, centered magnitude reached 472.978; for 40,
902.845. Materializing their squares in binary16 produced four infinities
in two rows in each case. The corresponding fp32 maximum variances were
331.947 and 1,471.263, both finite. This demonstrates a real intermediate
overflow hazard; it does **not** establish that overflow is the only ANE
fault.

The experimental divide-by-8/restore-by-64 rewrite preserved original CPU
logits exactly on 12 short multilingual and padded pairs. It did not repair
the ANE output, so it is rejected as a solution on this evidence.

The explicit-fp32 variant was also compared on 12 multilingual/padded pairs:
its maximum GPU-vs-CPU absolute logit difference was 0.01444579. The much
smaller single-pair delta above is not a whole-model error bound. A logit
delta is not a probability difference or a retrieval-metric change.

Small models with three fp16 identity matrix multiplications were used to
check square-by-Pow against square-by-Mul and negative against positive
reduction axes. The CoreML outputs of the two square variants matched each
other, as did the two mean variants. These controls do not support blaming
those individual function/axis choices alone. Their CPU differences include
the preceding matrix multiplications and cannot isolate one operator.

## Attention layout fault isolated with native Core ML

A later diagnostic used one sensitive pair (index 26 of the fixed 120-pair
screen), batch 1 and 128 tokens. The first attention stage took the identical
CPU-produced embedding-normalization output in every arm, with unchanged fp16
weights. The stage used one intra-op thread, with spinning disabled; the
complete-model screen used ten. This is a stage diagnostic, not a whole-model
error bound.

Tracing intermediate outputs located the first large deviation at the
transpose/reshape that merges heads. Native Core ML prediction, bypassing ORT,
confirmed that `ALL` returned a merged tensor exactly equal to the context
flattened **without** the required head/sequence transpose. The same compiled
model and inputs under `CPUAndGPU` returned the correct transpose and reshape.
All actual outputs were fp16; coordinate reads and stride-aware raw reads
agreed exactly. This excludes an ORT output-copy defect for this reproduction.

Making only the final head merge run on the host did not repair the stage:
its incoming context was already wrong. Materializing all four attention
transposes (Q, K, V and context) as bit-preserving host operations repaired
this stage:

| First attention stage, identical input | Max absolute output delta from CPU | Relative RMS delta from CPU |
| --- | ---: | ---: |
| Original, ALL | 150.734375 | 0.611757 |
| Four materialized transposes, CPU | 0 | 0 |
| Four materialized transposes, CPUAndGPU | 0.062500 | 0.000612 |
| Four materialized transposes, ALL | 0.031250 | 0.000657 |

The corrected stage's compute plan preferred ANE for the Q/K/V linear
partition (9 operations) and output projection (4 operations), and CPU for
the intervening attention partition (12 operations). These are compiler
preferences, not synchronized hardware counters. No stage speedup is claimed.
Extra trace outputs can alter compilation, so this fault must also be tested
in complete, uninstrumented model forwards.

Replacing the 96 transposes across the full model preserved all 120 CPU
logits bit for bit against the original native-normalization/GELU CPU graph.
The complete accelerated screen rejected the layout-only candidate: across
120 pairs, maximum absolute logit delta from its same-graph CPU reference was
0.13091183, against 0.11528683 for the original native-normalization/GELU ANE
arm. Mean absolute deltas were 0.01749032 and 0.01638205. Correcting the isolated
stage therefore did not improve the complete model. Its 50 compiled partitions
took 768.743 seconds to load cold in this exploratory run. Startup was shared
with other work and is not an accepted production startup measurement.

The unoptimized diagnostic host-copy loop's timings are excluded; the
replacement test target was compiled with `-C opt-level=3`. No product default
has changed on the strength of this stage result. The remaining layout-only
GPU timing arm was stopped after rejection, and an optimized CPU timing arm
was skipped. A smaller follow-up reuses the existing ORT fused attention kernel
and one shared ORT CPU normalization session with fp32 stash, rather than
shipping a custom attention or normalization implementation. A first version
that left its casts in the outer CoreML graph emitted an E5RT mask-output
compilation exception; its finite scores do not validate acceleration. The next
candidate places those casts inside the shared CPU attention session too.

The shared CPU normalization kernel passed a separate overflow check: 1,024
alternating fp16 values of +900 and -900 produced exactly alternating +1 and
-1. This proves the local fp32-stash contract; full-model accelerated precision
and retrieval acceptance remain pending.

[Apple's ANE transformer reference](https://machinelearning.apple.com/research/neural-engine-transformers)
uses a channels-first four-dimensional representation and avoids most
reshape/transpose operations. It supports investigating layout materialization
and representation; it does not identify this reproduction's compiler defect.

## Relevant primary sources

- [ONNX LayerNormalization](https://onnx.ai/onnx/operators/onnx__LayerNormalization.html):
  `stash_type` specifies the computation precision of normalization's first stage.
- [Apple typed execution](https://apple.github.io/coremltools/docs-guides/source/typed-execution.html):
  explicit fp32 types can use GPU, while restricting ANE eligibility.
- [PyTorch normalization precision report](https://github.com/pytorch/pytorch/issues/66707):
  fp16 normalization can overflow and accumulate divergence.
- [SLaNC](https://arxiv.org/html/2410.10553v1): offline, weight-based scaling
  addresses normalization's limited dynamic range. The fixed experimental
  factor 8 above is not an implementation or validation of SLaNC; scaling
  must account for both overflow and underflow and preserve epsilon semantics.
- [ORT CoreML static fp16 report](https://github.com/microsoft/onnxruntime/issues/32569):
  an independent report of wrong finite outputs. Its OS and graph differ;
  it does not identify this run's internal cause.
- [Weight encoding and ANE placement, revised September 2026](https://arxiv.org/html/2608.22110v2):
  matched normalization controls distinguish intermediate dtype from arithmetic
  formulation. Compiler preferences alone do not establish runtime execution;
  the study uses device exclusion and synchronized hardware counters too.

Cold model load/compilation took minutes and a compiled experimental cache
occupied about 5 GiB. Compute-plan profiling was enabled, so these are not
production startup measurements. Scoring arms run sequentially. Completed
compiled caches are retired after their scores and compute plans are saved;
source models and numerical logs are retained. Complete
product-path precision, latency, memory, disk and platform validation remains
necessary before accepting a default change.
