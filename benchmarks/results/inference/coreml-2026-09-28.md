# CoreML normalization investigation (2026-09-28)

These are numerical diagnostics and single-pair forward timings, not accepted
retrieval improvements. No nDCG/recall or energy gain is claimed.

## Conditions

- Apple M4, Mac16,12, 10 logical CPU cores, 32 GiB RAM.
- macOS 26.6.2, build 25G83; Rust `ort` 2.0.0-rc.13.
- `onnx-community/bge-reranker-v2-m3-ONNX`, immutable revision
  `6f5ff65298512715a1e669753bc754d2bc8f367b`, `onnx/model_fp16.onnx`.
- The same weights and input IDs in all arms. CPU uses this fp16 export too,
  **not** the product's normal CPU int8 export.
- Graph optimization level 3, 10 intra-op threads, spinning disabled. ORT
  profiling enabled; CoreML compute-plan profiling enabled where applicable.
- Query: `How does memory retrieval work?`
- Document: `A memory system stores evidence so that later questions can
  retrieve accurate facts. ` repeated twice, including the trailing space.
- Batch 1, 48 tokens, no padding in the timing pair. Warm median is passes
  3 through 8 of nine forwards. Separate runs on a shared machine, not rotated
  paired latency trials. Tokenization and complete retrieval are excluded.

## Results

| Original / static MLProgram, ALL | Mostly ANE | about 10.54 ms | -5.08593750 | **3.92899919** |
| 49 native fp16 LayerNormalization nodes / ALL | Mostly ANE | 10.762 ms | -1.14746094 | 0.00947737 |

ALL permits CPU, GPU and ANE; it does not prove ANE participation. The fp32
normalization variant's compute plan assigned 49 normalizations and all its
other reported operations to GPU. It must not be described as an ANE repair.

The original dynamic default NeuralNetwork arm supported only 52 of 1,420
nodes. Its nine-forward ORT trace attributed 2,175 ms to CPU kernels and
23 ms to CoreML kernels. Dynamic MLProgram covered 1,312 nodes but split into
51 partitions and was slower in the diagnostic. Static shapes reduced this
to two partitions; correct arithmetic remains a separate requirement.

## Numerical evidence

The CPU trace of the native-normalization graph found large intermediate
values. For normalization 38, centered magnitude reached 472.978; for 40,
902.845. Materializing their squares in binary16 produced four infinities
in two rows in each case. The corresponding fp32 maximum variances were
331.947 and 1,471.263, both finite. This demonstrates a real intermediate
overflow hazard; it does **not** establish that overflow is the only ANE
fault.

The experimental divide-by-8/restore-by-64 rewrite preserved original CPU
logits exactly on 12 short multilingual and padded pairs. It did not repair
the ANE output, so it is rejected as a solution on this evidence.

The explicit-fp32 variant was also compared on 12 multilingual/padded pairs:
its maximum GPU-vs-CPU absolute logit difference was 0.01444579. The much
smaller single-pair delta above is not a whole-model error bound. A logit
delta is not a probability difference or a retrieval-metric change.

Small models with three fp16 identity matrix multiplications were used to
check square-by-Pow against square-by-Mul and negative against positive
reduction axes. The CoreML outputs of the two square variants matched each
other, as did the two mean variants. These controls do not support blaming
those individual function/axis choices alone. Their CPU differences include
the preceding matrix multiplications and cannot isolate one operator.

## Relevant primary sources

- [ONNX LayerNormalization](https://onnx.ai/onnx/operators/onnx__LayerNormalization.html):
  `stash_type` specifies the computation precision of normalization's first stage.
- [Apple typed execution](https://apple.github.io/coremltools/docs-guides/source/typed-execution.html):
  explicit fp32 types can use GPU, while restricting ANE eligibility.
- [PyTorch normalization precision report](https://github.com/pytorch/pytorch/issues/66707):
  fp16 normalization can overflow and accumulate divergence.
- [SLaNC](https://arxiv.org/html/2410.10553v1): offline, weight-based scaling
  addresses normalization's limited dynamic range. The fixed experimental
  factor 8 above is not an implementation or validation of SLaNC; scaling
  must account for both overflow and underflow and preserve epsilon semantics.
- [ORT CoreML static fp16 report](https://github.com/microsoft/onnxruntime/issues/32569):
  an independent report of wrong finite outputs. Its OS and graph differ;
  it does not identify this run's internal cause.

Cold model load/compilation took minutes and a compiled experimental cache
occupied about 5 GiB. Compute-plan profiling was enabled, so these are not
production startup measurements. Only one large compiled candidate cache was
retained at a time; source models and numerical logs were retained. Complete
product-path precision, latency, memory, disk and platform validation remains
necessary before accepting a default change.
